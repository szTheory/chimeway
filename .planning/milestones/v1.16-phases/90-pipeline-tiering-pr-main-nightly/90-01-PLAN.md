<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Fork PR -> ci.yml execution | A `pull_request` from a fork can propose edits to `ci.yml` itself; the repo uses `pull_request` (not `pull_request_target`), so the fork's edited workflow runs with the fork's own limited, secret-less `GITHUB_TOKEN`. |
| `workflow_dispatch.inputs.run_nightly` -> job conditionals | A manually-supplied boolean input flows into `if:` expressions and shell string comparisons that decide which jobs execute. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-90-01 | Tampering | `workflow_dispatch.inputs.run_nightly` | low | accept | Boolean-typed input compared only via `==` inside `if:` expressions and a shell string comparison against the literal "true"; never interpolated into a `run:` shell command as free text. `actionlint`'s script-injection checks flag any future change that would violate this. |
| T-90-02 | Elevation of Privilege | `ci.yml` itself (fork PR edits) | low | accept | The repo already uses `pull_request` (not `pull_request_target`) everywhere; a fork PR's edits to `ci.yml` run with the fork's own limited token and cannot reach repo secrets or push/schedule-only lanes regardless of what the PR edits — unchanged by this phase. |
| T-90-04 | Denial of Service | `concurrency.group` (push vs. schedule collision) | medium | mitigate | `concurrency.group` is keyed on `github.event_name` (Task 1) so push and schedule runs on `main` can never share a cancellation group; `cancel-in-progress` is scoped to `pull_request` only. |
</threat_model>
