    Replace § "Transactional Enqueueing for Consistency" (lines 70-96) with engine-accurate prose and examples:

    1. **Clarify two transactions:** `Chimeway.trigger/3` always commits event + notification rows in its own `Repo.transaction/1` before calling the configured dispatcher. It does **not** accept `multi:` and does **not** return `{:ok, multi}`.

    2. **Pattern A (recommended for host app writes + notify):** Commit host `Ecto.Multi` first, then call `Chimeway.trigger/3` after `Repo.transaction/1` succeeds:

    ```elixir
    alias Ecto.Multi
    alias MyApp.Repo

    with {:ok, %{user: user}} <-
           Multi.new()
           |> Multi.insert(:user, %MyApp.User{name: "Alice", email: "alice@example.com"})
           |> Repo.transaction(),
         {:ok, _result} <-
           Chimeway.trigger(
             WelcomeNotifier,
             %{name: user.name, email: user.email},
             idempotency_key: "welcome-#{user.id}",
             tenant_id: user.tenant_id
           ) do
      :ok
    end
    ```

    3. **Pattern B (atomic delivery planning + Oban job insert):** When notification rows already exist and you need dispatch jobs in the **same** DB transaction as other host writes, call the Oban dispatcher directly:

    ```elixir
    alias Chimeway.Dispatch.Oban
    alias Chimeway.Repo
    alias Ecto.Multi

    multi =
      Multi.new()
      |> Multi.run(:host_work, fn _repo, _ -> {:ok, :done} end)

    # notifications must already be persisted (e.g. from a prior trigger)
    assert {:ok, _deliveries} = Oban.dispatch([notification], multi: multi)
    assert {:ok, _} = Repo.transaction(multi)
    ```

    4. Remove every occurrence of `multi:` passed to `Chimeway.trigger/3` and the false claim that trigger returns `{:ok, multi}`.

    5. Add one sentence pointing to `test/chimeway/dispatch/oban_transactional_test.exs` for rollback/commit proofs.
