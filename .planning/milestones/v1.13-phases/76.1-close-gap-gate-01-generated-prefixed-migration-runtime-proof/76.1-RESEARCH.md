### Pattern 1: Materialize Fixture Migrations Before Running Ecto.Migrator

**What:** Copy committed `TIMESTAMP_*.exs` fixture files into a temporary migration directory with deterministic numeric versions before calling `Ecto.Migrator.run/4`. [VERIFIED: test/chimeway/migration_contract_test.exs]

**When to use:** Use this for the generated-prefixed runtime bridge so the proof executes the same committed fixture root as installer-golden proof. [VERIFIED: test/fixtures/installer_golden_prefixed/STDOUT.txt] [VERIFIED: test/chimeway/migration_contract_test.exs]

**Example:**

```elixir
# Source: test/chimeway/migration_contract_test.exs
# Keep the version range disjoint from existing priv/repo migrations.
fixture_root
|> migration_order()
|> Enum.with_index(1)
|> Enum.each(fn {fixture_name, index} ->
  version = 20_260_101_000_000 + index
  dest = Path.join(migrations_path, "#{version}_#{String.replace_prefix(fixture_name, "TIMESTAMP_", "")}")
  File.write!(dest, File.read!(Path.join([fixture_root, "tree", "priv", "repo", "migrations", fixture_name])))
end)
```

### Anti-Patterns to Avoid

- **Schema clone as proof:** `CREATE TABLE ... LIKE public... INCLUDING ALL` bypasses the generated migration code path and leaves the GATE-01 gap open. [VERIFIED: test/support/prefixed_runtime_case.ex]
- **Migration-runner prefix flag:** Passing a migrator `prefix: "chimeway"` would weaken Phase 74's explicit-prefix generated migration contract. [VERIFIED: .planning/ROADMAP.md] [CITED: https://ecto-sql.hexdocs.pm/3.13.5/Ecto.Migrator.html]
- **GeneratedRepo-only proof:** `GeneratedRepo` is valid for installer proof but insufficient for runtime proof because Chimeway runtime APIs use `Chimeway.Repo`. [VERIFIED: test/chimeway/migration_contract_test.exs] [VERIFIED: lib/chimeway/repo.ex]
- **Sandbox dynamic migration:** Ecto documents that migrator execution needs at least two connections and cannot run dynamically under SQL Sandbox's single shared connection model. [CITED: https://ecto-sql.hexdocs.pm/3.13.5/Ecto.Migrator.html]

## Common Pitfalls

### Pitfall 1: Green Gate With the Wrong Schema Setup

**What goes wrong:** `mix verify.runtime_prefix` passes while the runtime schema was cloned from public DDL rather than created by generated prefixed migrations. [VERIFIED: local command run 2026-07-02] [VERIFIED: test/support/prefixed_runtime_case.ex]

**Why it happens:** The current helper checks fixture presence but calls `clone_public_chimeway_schema!()` when the prefixed schema is not ready. [VERIFIED: test/support/prefixed_runtime_case.ex]

**How to avoid:** Add an assertion or bridge test that verifies generated fixture migrations ran in the same database used by the runtime proof. [VERIFIED: test/chimeway/migration_contract_test.exs]

**Warning signs:** The code still contains `clone_public_chimeway_schema!`, or the runtime proof never calls `Ecto.Migrator.run/4` over `installer_golden_prefixed`. [VERIFIED: test/support/prefixed_runtime_case.ex] [VERIFIED: codebase grep]

### Pitfall 2: Dynamic Ecto.Migrator Under SQL Sandbox

**What goes wrong:** Migrator setup can fail before runtime assertions because migration execution uses multiple connections while SQL Sandbox expects a controlled single-connection test transaction. [CITED: https://ecto-sql.hexdocs.pm/3.13.5/Ecto.Migrator.html] [VERIFIED: .planning/phases/75-runtime-prefix-propagation/75-01-SUMMARY.md]

**Why it happens:** Ecto.Migrator documents that migration execution uses one connection for the migration lock and another to run migrations. [CITED: https://ecto-sql.hexdocs.pm/3.13.5/Ecto.Migrator.html]

**How to avoid:** Use a unique non-sandbox database/repo process for the bridge proof, or isolate migration setup outside normal sandbox ownership with an approach verified by a focused RED/GREEN test. [CITED: https://ecto.hexdocs.pm/3.13.5/Ecto.Repo.html] [CITED: https://ecto-sql.hexdocs.pm/3.13.5/Ecto.Migrator.html]

**Warning signs:** The proof runs migrations in `setup_all` of a sandboxed case and fails with ownership/process errors. [VERIFIED: .planning/phases/75-runtime-prefix-propagation/75-01-SUMMARY.md]

### Pitfall 3: Dynamic Repo Scope Does Not Cross Processes

**What goes wrong:** A dynamic repo proof can pass in the current process but fail for spawned workers if those workers do not inherit the dynamic repo selection. [CITED: https://hexdocs.pm/ecto/3.13.5/replicas-and-dynamic-repositories.html]

**Why it happens:** Ecto dynamic repo selection is process-local. [CITED: https://hexdocs.pm/ecto/3.13.5/replicas-and-dynamic-repositories.html]

**How to avoid:** Keep the bridge proof narrow and synchronous unless the planner explicitly arranges repo selection for spawned worker processes; rely on the existing broad runtime suite for worker coverage. [VERIFIED: test/chimeway/runtime_prefix_integration_test.exs] [CITED: https://hexdocs.pm/ecto/3.13.5/replicas-and-dynamic-repositories.html]

**Warning signs:** The new proof uses `perform_job/2`, Oban workers, or async tasks under a dynamic repo without setting the dynamic repo inside each process. [VERIFIED: test/chimeway/runtime_prefix_integration_test.exs] [CITED: https://hexdocs.pm/ecto/3.13.5/replicas-and-dynamic-repositories.html]

### Pitfall 4: Accidentally Moving Installer Proof Into ci-gate

**What goes wrong:** `install_golden_contract` becomes an unconditional `ci-gate` dependency, contradicting Phase 76's path-gated installer proof decision. [VERIFIED: .planning/phases/76-prefix-docs-demo-and-gates/76-03-SUMMARY.md] [VERIFIED: .github/workflows/ci.yml]

**Why it happens:** GATE-01 mentions prefixed install/runtime behavior, but Phase 76 intentionally made runtime proof unconditional and installer golden proof path-gated. [VERIFIED: .planning/phases/76-prefix-docs-demo-and-gates/76-03-SUMMARY.md]

**How to avoid:** Add the bridge proof to `verify.runtime_prefix` and leave `install_golden_contract` outside `ci-gate` unless user explicitly changes the release-gate policy. [VERIFIED: mix.exs] [VERIFIED: .github/workflows/ci.yml]

**Warning signs:** `ci-gate.needs` includes `install_golden_contract`, or release-gate tests are weakened to stop asserting the path-gated boundary. [VERIFIED: test/chimeway/release_gate_contract_test.exs] [VERIFIED: .github/workflows/ci.yml]
