<objective>
Emit durable progression signals from webhook feedback using the `Chimeway.Signal.track/4` boundary, bridging the gap between raw delivery feedback and abstract workflow evaluation.

Purpose: Allow host applications and default step-progression journeys to explicitly wait on `delivery.bounced` or `delivery.succeeded` signals via the generic v1.3 signal router.
Output: Feedback worker emits `Signal`s on successful persistence.
</objective>

<tasks>
<task type="tdd">
  <name>Process Feedback Signal Emission</name>
  <files>lib/chimeway/webhooks/process_feedback_worker.ex, test/chimeway/webhooks/process_feedback_worker_test.exs</files>
  <behavior>
    - When `Deliveries.record_attempt/2` succeeds, the worker formats an event name `chimeway.delivery.#{outcome}` (e.g. `chimeway.delivery.bounced`, `chimeway.delivery.succeeded`).
    - The worker extracts `delivery.tenant_id` and `delivery.actor_id` to call `Chimeway.Signal.track/4`.
    - The payload includes the `delivery_id` and the `status` outcome string. If bounced or failed, it also maps the error reason into the payload.
    - Tests assert that a `Chimeway.Signals.Signal` row is created and the `SignalRouterWorker` is enqueued for delivery outcomes.
  </behavior>
  <implementation>

Use `Chimeway.Signal.track(delivery.tenant_id, delivery.actor_id, "chimeway.delivery.#{outcome}", payload)`. Make sure the payload contains `delivery_id` and `status`. Add the payload modifications specified in `31-PATTERNS.md`. Reference the analog test patterns from `test/chimeway/signal_test.exs` mapped in PATTERNS.md.
  </implementation>
