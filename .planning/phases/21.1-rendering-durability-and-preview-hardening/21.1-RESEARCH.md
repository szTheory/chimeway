## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Phase 21.1 should stay tightly scoped to the three concrete review findings from
  `21-REVIEW.md`; planning should not reopen the larger rendering-contract architecture from Phase
  21.
- **D-02:** Planning for this phase should assume the recommendation style is already decided:
  research first, converge on one coherent architecture, and escalate only if a choice changes the
  public product model or conflicts with a locked project principle.

### Durable rendering declaration
- **D-03:** Chimeway should persist the normalized rendering declaration at trigger time on
  `Notification`, not only sanitized `render_assigns`. The durable declaration should include the
  per-channel render identity needed later by planning, for example a `render_channels` map keyed by
  channel with `render_key` and `render_version`.
- **D-04:** `DeliveryPlanning` must stop calling `Notifier.rendering/2` or
  `Notifier.resolve_rendering/3` during planning. Planning should read the persisted declaration and
  call `Rendering.render_delivery/4` only.
- **D-05:** Chimeway should keep the current lifecycle split: `Notification` stores the reusable
  durable declaration, `Delivery` stores the per-channel rendered execution artifact
  (`render_key`, `render_version`, `render_data`), and adapters remain dumb transport seams.
- **D-06:** Chimeway should reject the “persist minimal extra recipient fields and keep
  recomputing `rendering/2` later” approach. It is notifier-specific, easy to regress, and violates
  least-surprise durability.
- **D-07:** Chimeway should reject the “persist fully rendered output for every channel at trigger
  time” approach as the primary design. It widens the sensitive-data surface, bloats durable rows,
  and makes `Notification` too execution-aware.

### Preview API contract
- **D-08:** `Chimeway.preview_rendering/3` should remain the canonical non-bang public preview API
  and return tagged `{:ok, preview} | {:error, reason}` tuples for expected boundary failures.
- **D-09:** `preview_rendering/3` should validate notifier modules up front before resolving
  rendering and should return stable tagged reasons such as `:notifier_not_loaded` rather than
  bubbling `UndefinedFunctionError` for unloaded modules.
- **D-10:** Phase 21.1 should not add blanket exception rescue around the preview path. Real
  rendering bugs should still surface during tests and development; only the expected boundary
  failure of invalid/unloaded notifiers should be normalized.
- **D-11:** A future bang variant such as `preview_rendering!/3` is compatible with Elixir
  conventions, but it is optional and not required for Phase 21.1.

### Preview CLI safety and DX
- **D-12:** `mix preview.rendering` should stop using `Code.eval_string/1` and `Code.eval_file/1`
  for `params` and `recipient` input.
- **D-13:** The canonical rich input format for the Mix task should be JSON, with both inline JSON
  and file-based JSON variants. This matches normal Mix-task ergonomics, stays data-only, and keeps
  the task a thin wrapper over `Chimeway.preview_rendering/3`.
- **D-14:** The Mix task should add shallow repeated key-value flags as a convenience layer for
  small examples, while keeping file-based JSON as the preferred path for anything non-trivial or
  sensitive.
- **D-15:** If developers truly need executable Elixir for advanced preview experimentation, the
  documented escape hatch should be `mix run -e` or `iex -S mix`, not hidden code evaluation inside
  `mix preview.rendering`.

### Testing and developer ergonomics
- **D-16:** Phase 21.1 should add regression coverage proving planner-time rendering no longer
  depends on recipient fields that were available only at trigger time.
- **D-17:** Phase 21.1 should add a contract test proving planning/dispatch do not re-enter
  `Notifier.rendering/2` after trigger-time declaration persistence.
- **D-18:** Phase 21.1 should extend preview tests to cover invalid/unloaded notifier handling plus
  JSON/file parsing behavior in the Mix task, while preserving preview parity with the production
  rendering pipeline.
- **D-19:** Preview and render docs should optimize for least surprise and fast inspection:
  canonical library API first, then safe CLI examples, then optional host-app browser-style preview
  integrations if the host wants them.

### Explainability guardrails
- **D-20:** This phase should preserve Chimeway’s explainability posture while hardening rendering:
  durable render identity and machine-readable failure reasons should be queryable, but rendered
  bodies and sensitive payload details should remain excluded from operator-facing traces unless
  explicitly designed otherwise.
- **D-21:** If planning touches any rendering fallback behavior, hidden fallbacks should not become
  silent durable truth. Any fallback that affects the rendered artifact should either be disallowed
  or recorded explicitly enough that operators and developers can explain what happened later.

### the agent's Discretion
- Exact durable field/module naming for the persisted declaration, for example `render_channels`
  versus `render_declaration`, provided the stored shape remains explicit and channel-scoped.
- Exact JSON flag names and whether shallow convenience flags merge over file/inline JSON, provided
  the task stays data-only and easy to explain.
- Whether to keep `Notifier.validate_module!/1` as-is for Phase 21.1 or to stage a later cleanup
  around its non-bang semantics, provided the preview API contract stays stable.

### Deferred Ideas (OUT OF SCOPE)
- Browser-based or LiveDashboard preview UI in the core library.
- Broad rendering contract redesign beyond the three concrete review findings.
- New rendering channels, workflow/template editors, or hosted-style template lifecycle tooling.
- A restricted Elixir-literal input mode for the Mix task; JSON/file input is the default for this
  phase unless planning finds a compelling narrow safe parser worth adding.

## Summary

Phase 21.1 is a narrow hardening pass, not a rendering redesign. The current code already resolves rendering once at trigger time in `Chimeway.Trigger.notifications_attrs/4`, already materializes per-channel payloads through `Rendering.render_delivery/4`, and already exposes a pure preview surface through `Chimeway.preview_rendering/3`; the failures come from one planner-time re-entry seam and one unsafe CLI wrapper seam, not from the core render contract itself. [VERIFIED: lib/chimeway/trigger.ex, lib/chimeway/delivery_planning.ex, lib/chimeway/rendering.ex, lib/chimeway/rendering/preview.ex, .planning/phases/21-template-versioning-rendering-contracts/21-REVIEW.md]

The planning recommendation is to persist one normalized declaration snapshot on `Notification`, reuse that snapshot for every later planning/render step, keep preview non-bang with explicit tagged boundary errors, and make the Mix task a data-only wrapper over the same API. This matches the locked context, preserves Chimeway’s explainability posture, and minimizes new surface area because it extends existing seams instead of introducing a second rendering pipeline. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md, AGENTS.md, lib/chimeway.ex, lib/chimeway/delivery_planning.ex]

**Primary recommendation:** Add a durable `Notification`-level render declaration field, plan exclusively from that persisted snapshot, validate preview notifiers before resolution, and accept only JSON/data flags in `mix preview.rendering`. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md, lib/chimeway/trigger.ex, lib/chimeway/delivery_planning.ex, lib/chimeway/rendering/preview.ex, lib/mix/tasks/preview_rendering.ex]

## Architecture Patterns

### System Architecture Diagram

```text
Trigger.trigger/3
  -> Notifier.validate_module!/1
  -> Notifier.resolve_rendering/3
  -> Rendering.normalize_declaration/1
  -> sanitize assigns + persist Notification(render_assigns + render declaration snapshot)
  -> DeliveryPlanning.plan_notification/2
       -> read persisted declaration snapshot from Notification
       -> for each channel:
            Rendering.render_delivery/4
            -> Deliveries.plan_delivery/3
            -> Deliveries.apply_render_result/2
  -> dispatch path / preview path
       -> preview: validate notifier + read requested channel + render once
       -> dispatch: adapters consume Delivery.render_key/render_version/render_data only
```

The primary data-flow change for this phase is replacing planner-time `Notifier.resolve_rendering/3` with planner-time reads from a persisted declaration snapshot. [VERIFIED: lib/chimeway/trigger.ex, lib/chimeway/delivery_planning.ex, .planning/phases/21-template-versioning-rendering-contracts/21-REVIEW.md]

### Recommended Project Structure

```text
lib/chimeway/
├── trigger.ex                    # Persist render declaration snapshot at notification insert time
├── notifications/notification.ex # Add declaration field(s) + validation
├── delivery_planning.ex          # Read declaration snapshot; never re-enter notifier rendering
├── rendering.ex                  # Keep normalization/render contract authoritative
├── rendering/preview.ex          # Validate notifier boundary and preserve tagged errors
└── mix/tasks/preview_rendering.ex# JSON/file parsing wrapper over preview_rendering/3

```

The planner should treat this as one vertical slice across persistence, planning, preview, CLI parsing, and regression tests. ### Pattern 1: Persist the normalized declaration once

**What:** Persist the already-normalized render declaration on `Notification` at trigger time and reuse it later instead of recomputing it. [VERIFIED: lib/chimeway/trigger.ex, lib/chimeway/rendering.ex]
**When to use:** Always for any rendering data that affects later `Delivery` materialization. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md]
**Example:**

```elixir
# Source: lib/chimeway/trigger.ex + lib/chimeway/rendering.ex
with {:ok, declaration} <- Notifier.resolve_rendering(notifier, params, recipient) do
  row = %{
    render_assigns: sanitize_render_assigns(declaration.assigns),
    render_channels: declaration.channels
  }
end
```

### Pattern 2: Plan from persisted declaration, not notifier callbacks

**What:** `DeliveryPlanning` should read `Notification` declaration data and call `Rendering.render_delivery/4` for each channel. [VERIFIED: lib/chimeway/delivery_planning.ex, lib/chimeway/rendering.ex]
**When to use:** Every planning pass, including re-planning of an existing notification. [VERIFIED: test/chimeway/orchestration/delivery_planning_test.exs]
**Example:**

```elixir
# Source: lib/chimeway/delivery_planning.ex + lib/chimeway/rendering.ex
channel_rendering = notification.render_channels[channel]

Rendering.render_delivery(
  channel,
  channel_rendering.render_key,
  channel_rendering.render_version,
  notification.render_assigns
)
```

### Pattern 3: Keep preview as a thin safe wrapper

**What:** Validate the notifier boundary first, then reuse the same declaration and render code path as production. [VERIFIED: lib/chimeway/rendering/preview.ex, test/chimeway/rendering/preview_pipeline_test.exs]
**When to use:** Public preview API and Mix task execution. [VERIFIED: lib/chimeway.ex, lib/mix/tasks/preview_rendering.ex]
**Example:**

```elixir
# Source: lib/chimeway/rendering/preview.ex + https://hexdocs.pm/elixir/naming-conventions.html
with :ok <- Notifier.validate_module!(notifier),
     {:ok, recipient} <- fetch_required_option(opts, :recipient),
     {:ok, channel} <- fetch_required_channel(opts) do
  # delegate into the normal declaration/render path
end
```

### Anti-Patterns to Avoid

- **Planner-time notifier re-entry:** Re-calling `Notifier.resolve_rendering/3` in planning makes render identity depend on ephemeral recipient fields and reproduces WR-02 exactly. [VERIFIED: lib/chimeway/delivery_planning.ex, .planning/phases/21-template-versioning-rendering-contracts/21-REVIEW.md]
- **Catch-all preview rescue:** Converting all exceptions into tuples would hide render-contract bugs that current tests should catch. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md]
- **`Code.eval_*` parsing in CLI:** `Code.eval_string/3` and `eval_file/2` execute arbitrary Elixir with VM privileges and are not data parsers. [CITED: https://hexdocs.pm/elixir/Code.html]
- **JSON decode to atoms:** `Jason` warns that decoding user-controlled keys to atoms can become a DoS vector because atoms are not garbage collected. [CITED: https://hexdocs.pm/jason/Jason.html]

## Common Pitfalls

### Pitfall 1: Adding the new declaration field without backfilling old notifications

**What goes wrong:** Existing notifications inserted before the migration can have `render_assigns` but no durable channel identity snapshot, so planning cannot render later without either re-entry or a migration path. [VERIFIED: lib/chimeway/notifications/notification.ex, priv/repo/migrations/20260428123000_add_rendering_contract_fields.exs]
**Why it happens:** Phase 21 only added `render_assigns` on `Notification`; channel identities currently live only in runtime declaration results or later `Delivery` rows. [VERIFIED: lib/chimeway/notifications/notification.ex, lib/chimeway/delivery_planning.ex]
**How to avoid:** Add a migration plus application-level backfill strategy for preexisting rows, or make the planner reject rows missing the new snapshot with an explicit tagged error until migrated. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md, ASSUMED]
**Warning signs:** Notifications exist with non-empty `render_assigns` and empty/missing declaration data. [VERIFIED: lib/chimeway/notifications/notification.ex, PG query against `chimeway_test` showing existing rows]

### Pitfall 2: Reusing `metadata` as durable render truth forever

**What goes wrong:** `metadata` is currently a compatibility projection of sanitized assigns, not a full rendering declaration, so treating it as canonical durable truth hides the fact that per-channel identity is missing. [VERIFIED: lib/chimeway/trigger.ex, test/chimeway/rendering/render_identity_integration_test.exs]
**Why it happens:** `metadata` and `render_assigns` currently hold the same shape, which makes the absence of persisted channel identities easy to miss. [VERIFIED: test/chimeway/rendering/render_identity_integration_test.exs]
**How to avoid:** Store declaration data in an explicit field and keep `metadata` as a compatibility or operator surface only if still needed. [VERIFIED: .planning/phases/21.1-rendering-durability-and-preview-hardening/21.1-CONTEXT.md]
**Warning signs:** Planner code fetches rendering inputs from `notification.metadata` or rebuilds them from recipient metadata. [VERIFIED: lib/chimeway/delivery_planning.ex]

### Pitfall 3: Accepting JSON but decoding keys to atoms

**What goes wrong:** Atom decoding makes a local CLI convenience surface vulnerable to atom leaks if developers paste arbitrary data or expand the task beyond local-only use later. [CITED: https://hexdocs.pm/jason/Jason.html]
**Why it happens:** `Jason` supports atom decoding modes, and it is easy to choose them for ergonomic reasons. [CITED: https://hexdocs.pm/jason/Jason.html]
**How to avoid:** Keep default string keys and normalize downstream as maps with string keys, which already matches existing `render_assigns` usage. [VERIFIED: lib/chimeway/trigger.ex, test/chimeway/rendering/render_identity_integration_test.exs, CITED: https://hexdocs.pm/jason/Jason.html]
**Warning signs:** `Jason.decode(..., keys: :atoms)` or `:atoms!` appears in the Mix task. [CITED: https://hexdocs.pm/jason/Jason.html]
