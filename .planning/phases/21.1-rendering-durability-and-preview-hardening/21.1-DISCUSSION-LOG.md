## Research Synthesis

### Durable declaration vs recomputation
- Recommended: persist the normalized declaration once on `Notification`, then materialize the
  per-channel rendered artifact onto `Delivery`.
- Rejected: persisting only a few extra recipient fields and continuing planner-time recomputation.
  This remains brittle, notifier-specific, and easy to regress.
- Rejected: persisting fully rendered output for every channel at trigger time. That widens the
  sensitive-data surface and overloads the `Notification` row.

### Preview API error behavior
- Recommended: non-bang `preview_rendering/3` returns tagged tuples for expected boundary failures.
- Optional later addition: `preview_rendering!/3` if the project ever wants a raising variant.
- Rejected: letting invalid notifier modules crash through `UndefinedFunctionError`.
- Rejected: blanket rescue that would hide real rendering bugs.

### Safe preview CLI inputs
- Recommended: JSON as the canonical rich input format, plus JSON files and shallow repeated
  key-value flags for convenience.
- Rejected: keeping `Code.eval_string/1` / `Code.eval_file/1` with warnings only.
- Deferred: safe restricted Elixir literal parsing. Possible later, but not the default.

### Cross-ecosystem lessons
- Copy: Swoosh/Laravel-style preview ergonomics where preview reuses the real rendering path.
- Copy: explicit, typed/render-validated payload contracts rather than ad hoc maps.
- Avoid: Noticed/Laravel class-name durable identity defaults.
- Avoid: Symfony/Laravel transaction/job-boundary recomputation of rendering from mutable state.
