<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| notifier callback -> notification persistence | Trigger-time rendering data crosses from host notifier code into Chimeway durable storage |
| notification row -> planner render execution | Persisted declaration data becomes the canonical source for later delivery rendering |
| delivery render path -> operator traces | Render identity must stay explainable without exposing bodies or sensitive assigns |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21.1-01 | T | `lib/chimeway/trigger.ex` | mitigate | Persist only sanitized `render_channels` identity fields and sanitized `render_assigns`; never store rendered bodies on notifications. |
| T-21.1-02 | R | `lib/chimeway/delivery_planning.ex` | mitigate | Remove planner-time notifier re-entry and return `{:error, {:missing_render_declaration, channel}}` when durable declaration data is absent. |
| T-21.1-03 | I | `test/chimeway/integration/delivery_lifecycle_test.exs` | mitigate | Prove dispatch uses preplanned `render_data` and does not recreate sensitive render output from mutable runtime data. |
</threat_model>
