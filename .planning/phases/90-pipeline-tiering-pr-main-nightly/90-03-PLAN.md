<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Fork PR -> ci.yml execution | A `pull_request` from a fork can propose edits to `ci.yml` itself; the repo uses `pull_request` (not `pull_request_target`), so the fork's edited workflow runs with the fork's own limited, secret-less `GITHUB_TOKEN`. |
| `workflow_dispatch.inputs.run_nightly` -> job conditionals | A manually-supplied boolean input flows into `if:` expressions and shell string comparisons that decide which jobs execute. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-90-01 | Tampering | `workflow_dispatch.inputs.run_nightly` | low | accept | Boolean-typed input compared only via `==`/shell string comparison against the literal "true"; never interpolated into a `run:` shell command as free text. |
| T-90-02 | Elevation of Privilege | `ci.yml` itself (fork PR edits) | low | accept | The repo already uses `pull_request` (not `pull_request_target`) everywhere; a fork PR's edits run with the fork's own limited token and cannot reach repo secrets or the nightly-only lanes regardless of what the PR edits. |
| T-90-03 | Denial of Service | `ci-gate` needs: list scope creep | high | mitigate | Task 2 explicitly keeps `nightly-gate`/`nightly_cold_build`/`test_floor_1_17` out of `ci-gate`'s `needs:` list, and asserts this via the existing `extract_ci_gate_needs/1` helper so a future edit that accidentally widens `ci-gate` fails the contract suite immediately. |
| T-90-04 | Denial of Service | `concurrency.group` under the full nightly job graph | medium | mitigate | Task 3's live dispatch re-confirms Plan 90-01's concurrency fix holds even once the full nightly tier (4 additional jobs) is running concurrently with ordinary push/PR traffic. |
</threat_model>
