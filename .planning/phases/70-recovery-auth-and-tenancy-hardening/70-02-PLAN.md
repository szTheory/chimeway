<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Browser to LiveView `handle_event` | Recovery id, type, reason, and confirmation params are untrusted and may be replayed or modified. |
| LiveView socket to host authorization | Socket state can be stale; submit must re-check host auth at event time. |
| LiveView package to core recovery APIs | UI passes safe recovery opts into public Chimeway recovery functions. |
| Recovery UI to rendered HTML | Operator-facing evidence must avoid raw session, params, payload, provider body, secrets, tokens, auth codes, and full PII. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-70-02-01 | Elevation of Privilege | Recovery submit relying on mount authorization | mitigate | `RecoveryLive.handle_event("recover", ...)` calls `LiveAuth.ensure_authorized/3` with action, tenant_id, resource_id, recovery_type, and safe candidate facts per D-02 and D-03. |
| T-70-02-02 | Tampering | Client submits stale or forged candidate id/type | mitigate | Recovery submit validates/refetches selected candidate from the current tenant-scoped candidate list before authorization and core recovery calls. |
| T-70-02-03 | Repudiation / Tampering | Accidental destructive recovery submit | mitigate | Server-side reason plus explicit confirmation marker is required before authorization or recovery; disabled button is not the only guard. |
| T-70-02-04 | Information Disclosure | Recovery UI or metadata includes raw sensitive context | mitigate | UI displays only safe candidate/evidence fields and passes recovery options through `Context.recovery_opts/3`; tests assert raw session/params are absent from rendered recovery evidence. |
| T-70-02-SC | Tampering | Package manager installs | accept | No dependency install is planned; CSS stays in existing scoped files. |
</threat_model>
