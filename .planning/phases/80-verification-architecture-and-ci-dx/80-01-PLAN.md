<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR author → CI (pull_request event) | Untrusted contributor code runs the fast lanes and reports the required `pr-gate` check. |
| main push / workflow_dispatch → release gate | Trusted mainline / release-PR dispatch runs the full matrix behind `ci-gate`, polled by release/publish/automerge. |
| Branch protection (GitHub settings) → merge | Out-of-repo required-check config decides which aggregate must be green to merge. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-80-01 | Tampering | `ci-gate` `needs` / strictness | high | mitigate | Fold `install_golden_contract` into `needs` (D-05); contract test asserts 14 lanes and each lane present, so silently dropping a lane fails `mix ci.verify_gates`. |
| T-80-02 | Denial of Service | required-check pending trap (D-03 without pr-gate) | high | mitigate | `pr-gate` always runs on pull_request and reports a conclusion; the D-08 branch-protection swap is documented in Plan 04. Contract asserts `pr-gate` exists with the fast subset. |
| T-80-03 | Tampering | job-level `paths:` on a required-feeding lane | high | mitigate | Heavy lanes use an EVENT guard, not `paths:`; contract test asserts the four pr-gate lanes carry no `paths:`/`paths-ignore:`. |
| T-80-04 | Elevation of Privilege | untrusted PR code reaching release matrix | medium | mitigate | `ci-gate` and heavy lanes are event-guarded off pull_request, so the release/ecosystem matrix runs only on push/dispatch; release JS untouched (D-10). |
| T-80-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package installs; existing pinned action SHAs are reused unchanged. Cache-poisoning surface is handled in Plan 02. |
</threat_model>
