<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| trigger transaction -> workflow run state | Notification and workflow records must commit together or not at all |
| workflow current state -> workflow transition log | Current truth and historical why-data must stay consistent under retries and duplicates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-04 | T | `lib/chimeway/trigger.ex` | mitigate | Use one `Ecto.Multi` to persist notifications, runs, and initial transitions atomically. |
| T-24-05 | R | workflow transition history | mitigate | Record explicit `workflow_started` and `step_activated` reasons on append-only rows instead of inferring initial state from timestamps. |
| T-24-06 | D | duplicate trigger path | mitigate | Reuse event idempotency and deterministic notification ordering so duplicate trigger attempts do not create extra run rows. |
</threat_model>
