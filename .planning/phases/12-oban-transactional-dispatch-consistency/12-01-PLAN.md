# Plan 12-01: Atomic Dispatch Restructure

**Phase:** 12 — Oban Transactional Dispatch Consistency
**Plan:** 12-01
**Objective:** Restructure `Chimeway.Dispatch.Oban.dispatch/2` so delivery planning and job enqueue execute inside a single `Ecto.Multi`-backed transaction, eliminating the planning-before-transaction gap and the atom table exhaustion risk.
**Requirements:** [INTG-03, DLVR-04]
**Wave:** 1 (no dependencies within phase)

---

## Context

### Problem

`lib/chimeway/dispatch/oban.ex` has two defects:

1. **Atomicity gap** — `plan_notifications/2` commits delivery rows before the `Ecto.Multi` transaction starts (line 38). A failed enqueue cannot roll back already-committed planning rows, leaving orphaned `:pending` delivery rows with no corresponding Oban job.

2. **Atom table risk** — `String.to_atom("enqueue_delivery_#{delivery.id}")` (line 68) creates atoms from PostgreSQL UUIDs. Each unique UUID creates a new atom. The Erlang atom table limit is 1,048,576 entries; sustained volume causes a system crash.

### Locked Decisions (CONTEXT.md)

- **D-01:** Use tuple step names `{:enqueue_delivery, idx}` — or eliminate per-job steps entirely by using a single `Ecto.Multi.run(:enqueue_jobs, ...)` wrapper.
- **D-02:** Wrap `plan_notifications/2` in `Ecto.Multi.run/3` so its `Repo.insert` calls execute on the checked-out connection.
- **D-03:** Accept caller-provided `:multi` as base; prepend caller steps before planning and enqueue steps.
- **D-04:** Map step failures to caller error shapes: planning step → `{:error, {:planning_failed, reason}}`; enqueue step → `{:error, reason}`; caller steps → `{:error, reason}` (no raw multi step tuples).
- **D-05:** Merge non-multi and multi paths using `base_multi = Keyword.get(opts, :multi, Ecto.Multi.new())` — eliminates two-branch implementation.
- **D-06:** Do not change `DeliveryPlanning.plan_notifications/2` contract.

### Target File

`lib/chimeway/dispatch/oban.ex` — the only file requiring changes.

## Tasks

### Task 1 — Merge dispatch paths into unified multi implementation

**What:** Replace the current two-branch `dispatch/2` (with/without `:multi` opt) and the two `enqueue_deliveries` clauses with a unified implementation using `base_multi = Keyword.get(opts, :multi, Ecto.Multi.new())`.

**How:**

```elixir
@impl Chimeway.Dispatch
def dispatch(notifications, opts) when is_list(notifications) do
  base_multi = Keyword.get(opts, :multi, Ecto.Multi.new())

  multi =
    base_multi
    |> Ecto.Multi.run(:plan_notifications, fn _repo, _changes ->
      DeliveryPlanning.plan_notifications(notifications, opts)
    end)
    |> Ecto.Multi.run(:enqueue_jobs, fn _repo, %{plan_notifications: deliveries} ->
      deliveries
      |> Enum.filter(fn d -> d.status == :pending end)
      |> Enum.reduce_while({:ok, []}, fn delivery, {:ok, acc} ->
        case enqueue_one(delivery) do
          {:ok, job} -> {:cont, {:ok, [job | acc]}}
          {:error, reason} -> {:halt, {:error, reason}}
        end
      end)
    end)

  case Repo.transaction(multi) do
    {:ok, %{plan_notifications: deliveries}} ->
      {:ok, deliveries}

    {:error, :plan_notifications, reason, _changes} ->
      {:error, {:planning_failed, reason}}

    {:error, _step, reason, _changes} ->
      {:error, reason}
  end
end
```

Notes:
- `enqueue_one/1` (existing private function, lines 78–87) is reused as-is — no change needed.
- `pending_deliveries/1` private helper becomes unused after merge — remove it.
- `enqueue_deliveries/2` private functions (both clauses) become unused — remove them.
- `planning_failed/1` private function becomes unused — remove it.

**Acceptance criteria:**
- `dispatch/2` has one implementation clause handling both `:multi` and no-`:multi` cases.
- `plan_notifications/2` is called inside `Ecto.Multi.run`, not before the multi pipeline.
- No `String.to_atom/1` call remains in the module.
- Removed private helpers: `pending_deliveries/1`, `enqueue_deliveries/2` (both clauses), `planning_failed/1`.

**Done condition:** `grep -n "String.to_atom" lib/chimeway/dispatch/oban.ex` returns no matches; `grep -n "enqueue_deliveries\|pending_deliveries\|planning_failed" lib/chimeway/dispatch/oban.ex` returns no matches.

### Task 2 — Verify error shape mapping covers all step failure paths

**What:** Confirm the `case Repo.transaction(multi)` error mapping handles all failure cases correctly per D-04 and existing caller contract.

**Verify these paths:**

| Failure path | Expected return |
|---|---|
| `:plan_notifications` step returns `{:error, reason}` | `{:error, {:planning_failed, reason}}` |
| `:enqueue_jobs` step returns `{:error, reason}` | `{:error, reason}` |
| Caller-provided `:multi` step fails | `{:error, reason}` (step reason, no raw multi tuple) |
| All steps succeed | `{:ok, deliveries}` |

**Acceptance criteria:**
- `case Repo.transaction(multi)` match arm for `:plan_notifications` step is `{:error, :plan_notifications, reason, _changes} -> {:error, {:planning_failed, reason}}`.
- All other `{:error, _step, reason, _changes}` cases return `{:error, reason}`.
- No arm returns a raw `{:error, step_name, reason, changes}` tuple to callers.

**Done condition:** Read `lib/chimeway/dispatch/oban.ex` and confirm the `case Repo.transaction` block matches the table above. No `{:error, step, reason, changes}` tuple passes through to callers.

**Acceptance criteria:**
- All tests in `oban_transactional_test.exs` and `oban_test.exs` pass.
