<interfaces>
`Chimeway.Adapters.APNS.deliver/2` is the only accepted tracer entry. It calls `Transport.push/3`; the optional default path calls synchronous `Pigeon.push/3` and maps a returned notification with `response: :success` to `%Transport.Result{outcome: :accepted}` and then `provider_accepted`.

`PigeonAdapter.process_end_stream/2` owns the queue pop. Recognized bounded 410 and retryable error streams remain Chimeway-closed results. Every other correlated stream must use Pigeon 2.0.1's normal `Pigeon.Configurable.handle_end_stream(config, stream, notification)` behavior so status 200 reaches the original callback as success.

The enabled fixture remains pinned to Pigeon 2.0.1 per D-14. Pigeon 2.0.1 constrains HTTPoison below 3, but the APNs-only supported fixture can explicitly override that unused provider branch to HTTPoison 3.0.0 and Hackney 4.7.4; this exact graph was resolved and compiled during planning. The committed enabled lock and `mix hex.audit` determine whether that graph remains acceptable.
</interfaces>
</context>

<gap_closure_root_cause>
The always-compiled Pigeon-neutral callback added for downstream opt-in sends every correlated stream through `runtime_closed_result/1`; its catch-all manufactures a rejected `unrecognized_provider_response`, unlike the optional compile-time implementation that delegates unknown/ordinary streams to Pigeon. Separately, the fixture resolves a fresh advisory-bearing legacy Hackney graph and treats advisory output from dependency resolution as informational. Both failures are in the packaged adopter path and must close in the same required `mix verify.apns` lane.
</gap_closure_root_cause>

</assumption_delta_decision>
