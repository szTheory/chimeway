  <files>lib/chimeway/adapter.ex</files>
  <read_first>.planning/phases/02-first-outbound-delivery-slice/02-RESEARCH.md, .planning/phases/02-first-outbound-delivery-slice/02-CONTEXT.md</read_first>
  <action>Create `lib/chimeway/adapter.ex` defining `Chimeway.Adapter` as an Elixir behaviour with one required callback:

```elixir
@callback deliver(delivery :: Chimeway.Delivery.t(), config :: keyword()) ::
            {:ok, map()} | {:error, atom(), map()}
```

Return contract (document in @moduledoc and @doc for deliver/2):
- `{:ok, meta}` — provider accepted the delivery. `meta` is a compact map written to `chimeway_delivery_attempts.provider_response`. Adapters MUST redact sensitive fields (password, token, secret, api_key, auth) from meta before returning.
- `{:error, reason_class, detail}` — delivery failed. `reason_class` MUST be one of `:temporary | :permanent | :bounced`. `detail` is a compact map with no PII and no full provider response bodies.

Document explicitly in @moduledoc:
1. Adapters must not call back into notifier modules to render content — all rendered content must arrive pre-populated on the `%Chimeway.Delivery{}` struct.
2. Adapter config (API keys, base URLs) must be read at call time via `Application.get_env/3`, never in module attributes or at compile time. This supports test overrides via `Application.put_env` and runtime environment switching.
3. Outcome classification (`:succeeded`, `:failed`, `:rejected`, `:bounced`) is the dispatcher's responsibility, not the adapter's. Adapters return raw results; the dispatcher maps them to Chimeway's state machine.</action>
  <verify>rg "@callback deliver" lib/chimeway/adapter.ex && rg "temporary.*permanent.*bounced\|permanent.*bounced" lib/chimeway/adapter.ex && rg "@moduledoc" lib/chimeway/adapter.ex && mix compile --warnings-as-errors</verify>
  <acceptance_criteria>
    - Chimeway.Adapter defines @callback deliver/2 with the exact two-clause return typespec
    - @moduledoc documents :temporary | :permanent | :bounced reason classes and redaction requirement
    - @moduledoc states that adapters must not render content (no notifier callbacks)
    - @moduledoc states that adapter config must be read via Application.get_env at call time
    - A module using @behaviour Chimeway.Adapter that omits deliver/2 produces a compiler warning (Elixir default)
  </acceptance_criteria>
  <done>Chimeway.Adapter behaviour is defined and documented; any module implementing the behaviour without deliver/2 gets a compile-time warning.</done>

<task type="auto">
  <name>Task 02-02-03: Wire Chimeway.Dispatch.Sync to adapter, outcome classification, and atomic attempt recording</name>
  <files>lib/chimeway/dispatch/sync.ex</files>
  <read_first>lib/chimeway/dispatch/sync.ex, lib/chimeway/deliveries.ex, lib/chimeway/delivery.ex, lib/chimeway/adapter.ex, lib/chimeway/adapters/test.ex</read_first>
  <action>Replace the Chimeway.Dispatch.Sync stub body with the full sync dispatch pipeline. The dispatch/2 function receives a list of notifications and should dispatch each delivery associated with those notifications.

Full dispatch logic for each delivery:

1. **Terminal state guard**: if `delivery.status in [:succeeded, :suppressed, :cancelled]`, return `{:ok, delivery}` immediately — no adapter call, no attempt row. Prevents double-dispatch.

2. **Transition to :dispatched**: call `Chimeway.Deliveries.transition_status(delivery, :dispatched)`. This must succeed before the adapter is called. If it fails, return the error.

3. **Resolve adapter module**: `adapter = Application.get_env(:chimeway, :adapter, Chimeway.Adapters.Logger)`

4. **Read adapter config**: `adapter_config = Application.get_env(:chimeway, [:adapters, delivery.channel], [])`

5. **Call adapter**: `adapter.deliver(delivery, adapter_config)`

6. **Classify outcome** (in the dispatcher, NOT the adapter):
   - `{:ok, meta}` → `attempt_outcome: :succeeded`, `delivery_status: :succeeded`, `provider_response: meta`
   - `{:error, :temporary, detail}` → `attempt_outcome: :failed`, `delivery_status: :failed`, `provider_response: detail`
   - `{:error, :permanent, detail}` → `attempt_outcome: :rejected`, `delivery_status: :failed`, `provider_response: detail`
   - `{:error, :bounced, detail}` → `attempt_outcome: :bounced`, `delivery_status: :failed`, `provider_response: detail`

7. **Atomic attempt + final status** (single Ecto.Multi): call `Chimeway.Deliveries.record_attempt(delivery, %{outcome: attempt_outcome, provider_response: provider_response})`. The record_attempt/2 implementation from 02-01 handles both the attempt insert and the delivery status transition atomically.

8. Return `{:ok, updated_delivery}` or `{:error, reason}`.

The outer dispatch/2 function iterates over deliveries (loaded via Chimeway.Deliveries for each notification) and returns `{:ok, results}` where results is the list of per-delivery outcomes.

Write targeted tests (can be in test/chimeway/dispatch/sync_test.exs):
- Trigger → adapter {:ok, meta} → delivery status: succeeded, attempt outcome: :succeeded, attempt row exists
- Adapter {:error, :temporary, detail} → delivery status: failed, attempt outcome: :failed
- Adapter {:error, :permanent, detail} → delivery status: failed, attempt outcome: :rejected
- Dispatch called on :succeeded delivery → {:ok, delivery} returned, no second attempt row created
- Atomicity: simulate a status update failure and confirm attempt row is also absent</action>
  <verify>rg "terminal.*succeeded.*suppressed.*cancelled\|@terminal_states\|when status in" lib/chimeway/dispatch/sync.ex && rg "Application.get_env.*adapter\|adapter\\.deliver" lib/chimeway/dispatch/sync.ex && rg "attempt_outcome\|delivery_status\|:succeeded\|:rejected\|:bounced" lib/chimeway/dispatch/sync.ex && mix test --seed 0</verify>
  <acceptance_criteria>
    - A full trigger → dispatch → attempt cycle produces: delivery row (status: :succeeded) + attempt row (outcome: :succeeded) when adapter returns {:ok, meta}
    - Adapter returning {:error, :temporary, detail} → attempt row (outcome: :failed), delivery status :failed
    - Adapter returning {:error, :permanent, detail} → attempt row (outcome: :rejected), delivery status :failed
    - Adapter returning {:error, :bounced, detail} → attempt row (outcome: :bounced), delivery status :failed
    - Dispatch called on a :succeeded delivery returns {:ok, delivery} without creating a second attempt row
    - Attempt row insert and delivery status transition are atomic: if status update fails, attempt row is also absent
    - mix test passes for the full suite
  </acceptance_criteria>
  <done>Sync dispatch path is fully wired — trigger creates deliveries, sync dispatcher calls adapter, classifies outcome, and persists attempt + final status atomically.</done>
