<objective>
Thread the host-supplied `tenant_id` through the trigger pipeline so trigger-created `WorkflowRun` rows carry the host's real tenant identity instead of the hardcoded literal `"default"`. Add an end-to-end integration test that proves `Trigger.trigger/3 -> Workflows.explain/2` works for a real tenant string.

Purpose: Phase 27 added tenant scoping to `route_signal/1`, `explain/2`, and `list_traces/3`, but `create_initial_run/4` stamps every trigger-created run with `tenant_id: "default"`. In any multi-tenant deployment, calling `Workflows.explain("acme", run.id)` returns `{:error, :not_found}` and `route_signal/1` never matches trigger-created runs. The inspection API and the routing API are both structurally unreachable for normal trigger flows. This plan closes that gap end-to-end.
Output: A `tenant_id` parameter threaded from `Chimeway.Trigger.trigger/3` opts through `do_trigger` and `insert_workflow_runs` into `Workflows.create_initial_run/5`, plus an integration test that asserts the round-trip works.

**Closes gaps:** CR-04 (BLOCKER).

**Why Wave 6 (depends on 27-04 AND 27-06):** This plan touches `lib/chimeway/workflows.ex` (`create_initial_run/4 -> /5`). Plan 27-06 also touches `lib/chimeway/workflows.ex` (`route_signal/1`, `list_traces/3`). To honor the no-overlap-in-same-wave rule, this plan runs strictly after 27-06. It also depends on 27-04 because the new tenant_id changeset validation must be in place before threading real tenant strings (so an empty string from a buggy host call fails at changeset time, not at insert time).
</objective>
