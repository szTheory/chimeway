## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Redaction marker gaps, status dot gaps, field hints |
| sm | 8px | Inline masked identity spacing, compact row metadata, timeline detail gaps |
| md | 16px | Default card padding, list gaps, form gaps, alert padding |
| lg | 24px | Detail panel padding, section heading separation, Definitions table wrapper padding |
| xl | 32px | Main content padding on desktop, two-column trace/detail/recovery grid gaps |
| 2xl | 48px | Major vertical section separation only |
| 3xl | 64px | Page-level spacing only; avoid inside cards, tables, timeline entries, and status badges |

Exceptions: retain Phase 69/70 exceptions. Navigation targets, row buttons, search submits, recovery submits, and confirmation controls must be at least 44px high on mobile and 40px high on desktop. Read-only status pills may be 26px minimum height. 1px borders and 3px focus outlines are allowed. No new raw spacing values except existing tokenized CSS values, 1px borders, and the existing 3px focus treatment.

Implementation contract: reuse `--cw-space-*` tokens under `.chimeway-admin`. Phase 71 additions should extend existing `.cw-status`, `.cw-alert`, `.cw-summary-list`, `.cw-timeline__details`, `.cw-empty`, `.cw-table`, `.cw-copy-id`, and optional presenter classes. Do not add page-local spacing one-offs for redaction or lifecycle labels.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.35 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.15 |

Typography contract:

- Use exactly the four Phase 69 font-size tokens: `--cw-font-size-label`, `--cw-font-size-body`, `--cw-font-size-heading`, and `--cw-font-size-display`.
- Use exactly two weights: `--cw-font-weight-regular: 400` and `--cw-font-weight-semibold: 600`.
- Masked recipient values, notification keys, version strings, delivery IDs, event IDs, tenant IDs, correlation IDs, error classes, and timeline detail values must use `overflow-wrap: anywhere` and `min-width: 0` in flex/grid/table containers.
- Lifecycle labels must be sentence case and short enough to fit status pills at 390px mobile width: `Sent`, `Provider accepted`, `Delivered`, `Suppressed`, `Retryable failure`, `Terminal failure`.
- Do not use viewport-scaled type or negative letter spacing.

Source: Phase 69 typography contract, REQUIREMENTS DES-03, and Phase 71 CONTEXT D-08/D-10.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | light `#fffdf8`; dark `#07131a` | Root page background and broad reading surface |
| Secondary (30%) | light `#ffffff` / `#f7f4ea`; dark `#10232c` / `#0b1b23` | Cards, sidebar, nav, rows, inputs, tables, timeline entries, summary lists |
| Accent (10%) | light `#0e7c86`; dark/system-dark `#9adbcf` | Active nav item, selected rows, primary search/open CTAs, focus-adjacent highlights, `.cw-eyebrow` labels |
| Destructive | light `#b83232`; dark `#ffb3b3` button token | Recovery submit action and danger/error state only |

Accent reserved for: active navigation, primary trace/search CTA, selected recovery/trace row, focused or selected row emphasis, `.cw-eyebrow`, and informational emphasis that helps identify the current operator context. Accent must not be used to decorate every redacted value, every link, or all status badges.

Semantic status color contract:

- `Delivered`, `Sent`, and `Provider accepted` use success tone only when backed by the corresponding durable fact; provider acceptance must not be styled or labeled as delivered.
- `Suppressed` uses warning tone.
- `Retryable failure` uses warning tone when retry or pending eligibility remains.
- `Terminal failure` uses danger tone.
- Unknown or DB-inferred history states use neutral/info tone with explicit copy, not alarming danger styling.
- Redacted values use normal foreground or muted text. Do not color redaction masks as errors; privacy preservation is expected behavior.

Source: Phase 69/70 color contracts, `chimeway_admin/priv/static/chimeway_admin.css`, REQUIREMENTS PRIV-01/EXPL-01, and Phase 71 CONTEXT D-10/D-11.

## Interaction Contract

| Surface | Contract |
|---------|----------|
| DTO boundary | LiveViews render only stable admin DTO/explanation fields. Do not assign raw Ecto schemas, raw payloads, render assigns/data, provider bodies, session params, auth codes, tokens, secrets, or full PII. |
| Redacted identity display | Recipient identities remain visible only in masked form through `ChimewayAdmin.Redaction.redact_recipient/1`. Examples: `user:***123`, `a***@example.test`, or opaque `ab***xyz`. Full recipient PII must never appear in rendered HTML. |
| Positive privacy feedback | Redaction should be visible through masked values and useful safe facts, not blank UI. Tests must prove absence of sensitive fixtures and presence of masked identity/status/key/correlation facts. |
| Timeline details | Timeline detail rendering continues through `Redaction.safe_timeline_detail/1`. Only allowlisted keys render; sensitive key names such as token, secret, password, api_key, auth, session, params, payload, render_data, and provider_body do not render. |
| Status presenter | Centralize display labels in `ChimewayAdmin.Components.Status` or a nearby presenter. Do not change durable core status atoms. |
| Lifecycle wording | Distinguish `Sent`, `Provider accepted`, `Delivered`, `Suppressed`, `Retryable failure`, and `Terminal failure`. Use `Delivered` only when durable provider feedback proves delivery. |
| Trace detail | Current state, `Why`, `What`, and timeline sections must keep safe explanation facts visible after redaction: status label, suppression reason, planning reason, last attempt summary, next eligible time, notification key, channel, masked recipient, render identity, and safe IDs. |
| Dashboard | Metrics and recent problem rows may show aggregate outcome counts, notification key, masked recipient, channel, and safe status label. They must not show payload/render/provider/session details. |
| Feed | Search accepts full recipient identity as operator input, but result rows render masked recipients only. Empty results must not echo the full query back into the page body. |
| Recovery | Preserve Phase 70 confirmation behavior and safe evidence boundary. Recovery candidate/review UI may show type, notification key, reason, tenant ID, correlation ID, resource ID, and status only. |
| Definitions | Describe the screen as DB-inferred durable key/version history from persisted Chimeway rows. Do not claim code registry, source-code skew detection, notifier module discovery, or module inventory. |
| Focus and keyboard | Existing focus-visible behavior remains: 3px outline, 3px offset, no transform on focus. Redaction/status changes must not introduce layout shifts that move focused controls. |
| Motion | Use Phase 69 motion only: 120ms color/border/background transitions and 80ms pressed feedback. Reduced-motion media query must reduce transitions to near-zero. |

Out of scope: Phase 71 must not add browser-smoke gate work, `mix verify.admin` composition, public docs integration copy, arbitrary provider-body inspection, source-code registry detection, template editing, or broad DTO API churn.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Search traces |
| Secondary CTA | Back to Trace Lookup |
| Empty state heading | No deliveries found |
| Empty state body | Try a full recipient identity, correlation ID, or remove the notification key filter. |
| Feed empty state heading | No feed rows found |
| Feed empty state body | Try a full recipient identity from the host app. |
| Definitions empty state heading | No definitions seen |
| Definitions empty state body | Persisted notification keys and versions will appear after Chimeway records events or deliveries. |
| Trace not found heading | No delivery exists |
| Trace not found body | No delivery exists for ID {delivery_id}. |
| Error state | Unable to render the redacted explanation. Refresh the page; if it repeats, check server logs with the delivery ID. |
| Destructive confirmation | Recover this {event\|delivery}: require `Recovery reason` plus the existing confirmation marker before submission. |

Lifecycle label copy:

| Operator Label | Meaning |
|----------------|---------|
| Sent | Chimeway created or dispatched the delivery internally, but external delivery feedback is not proven. |
| Provider accepted | The provider accepted the send attempt; do not imply final recipient delivery. |
| Delivered | Durable provider feedback proves delivery. |
| Suppressed | Chimeway intentionally did not send because a suppression rule/reason applied. |
| Retryable failure | The last failure is explainable and retry/recovery may still be possible. |
| Terminal failure | Chimeway has durable evidence that the delivery will not proceed without new action. |

Definitions screen copy:

- Page description: `Durable notification keys and versions inferred from persisted Chimeway events and deliveries.`
- Section label: `Definitions seen in this app`
- Forbidden words/claims in rendered Definitions copy unless later implemented: `code registry`, `source skew`, `notifier module discovery`, `module inventory`, `loaded modules`, `source code scan`.

Copy source: existing `TraceSearchLive`, `TraceDetailLive`, `FeedLive`, `RecoveryLive`, `DashboardLive`, Phase 71 CONTEXT D-09 through D-13, and REQUIREMENTS EXPL-01/EXPL-02.

## Redaction Evidence Contract

| Surface | Sensitive Values That Must Be Absent | Useful Facts That Must Remain Present |
|---------|--------------------------------------|---------------------------------------|
| Dashboard | raw payloads, render assigns/data, provider bodies, tokens, secrets, auth codes, full recipient PII | aggregate counts, notification key, masked recipient, channel, safe status label, recovery count |
| Trace Detail | raw payloads, render assigns/data, provider bodies/responses, metadata secrets, session/params, tokens, secrets, auth codes, full recipient PII | status label, suppression/planning reason, sanitized last attempt, next eligible time, notification key, channel, masked recipient, render identity, safe timeline details |
| Feed | full recipient PII in results, payload/render/provider fields, tokens/secrets/auth codes | searched state, notification key/version, masked recipient, state label, channel summary, safe correlation ID |
| Recovery | raw session, params, payloads, provider bodies, secrets, tokens, auth codes, full PII | type, notification key, reason, tenant ID, resource/correlation ID, confirmation marker, safe flash outcome |
| Definitions | payload/render/provider/session details, full PII, code-registry or source-skew claims | notification key, version, channels, event count, recipient count, delivery count, last seen timestamp, DB-inferred wording |

Acceptance expectation: rendered LiveView tests assert both `refute html =~ sensitive_fixture_value` and `assert html =~ expected_safe_or_masked_value` for every listed surface.
