<objective>
Close gap WR-02 (PARTIAL) from `25-VERIFICATION.md`: `temporary_failure` is a branchable curated outcome derived from a non-terminal `:failed` delivery row, which means a notifier authoring `on_outcome temporary_failure -> escalate_to_email` will fire `escalate_to_email` on the FIRST transient failure (before any retry has been attempted). The 25-02 plan called this out as intentional, but the contract obscures the operational consequence and there is no documentation warning at either the authoring boundary (`Chimeway.Notifier`) or the runtime mapping site (`Chimeway.Workflows.ProgressionOutcome`).

**Resolution choice (locked, per VERIFICATION.md two-option requirement):** Option (b) — document the early-fire behavior in BOTH moduledocs (notifier.ex AND progression_outcome.ex) and recommend pairing `on_outcome temporary_failure` rules with idempotency keys at the destination step. NOT option (a) (removing `temporary_failure` from the vocabulary).

Rationale for choosing (b):
1. Plan 25-01 explicitly locked the curated D-04 vocabulary including `temporary_failure` ("delivered, suppressed, temporary_failure, retries_exhausted, permanent_failure, bounced") and Plan 25-02 implemented the early-fire semantics deliberately ("a persisted `delivery.status == :failed` row may advance the run immediately"). Removing `temporary_failure` would invalidate locked decisions D-04 and the Plan 25-02 contract.
2. The early-fire semantics ARE the intended behavior for some workflow shapes (e.g., "if the first attempt times out, immediately try a different channel while the original retries"). Removing the option closes off legitimate use cases.
3. The gap identified by the verifier is specifically about the missing documentation, not about the contract being wrong. Adding the warning closes the gap without rewriting any locked decision.

Output: warning sections added to `@moduledoc` of both `lib/chimeway/notifier.ex` and `lib/chimeway/workflows/progression_outcome.ex`, plus an inline comment near the `:failed -> :temporary_failure` mapping clause referencing the moduledoc.
</objective>
